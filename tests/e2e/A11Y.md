# Aria web — accessibility checklist (Wave 5, task 5.4)

Checked 2026-10-10 against `npm run dev` (local stack) in Chrome with device emulation
(`iphone-15`, `desktop`) and the screenshot set (375 / 393 / 430 / 1280 × light / dark / reduced
motion). **Automated** = asserted on every page by `tests/e2e/pages.spec.ts` (no axe; the checks
live in `tests/e2e/support/audit.ts`). **Manual** = looked at by hand or covered by a flow test.

## Known gaps (not fixable in presentation code)

- `/email/<bad id>` returns HTTP **200** with the not-found UI + `noindex` (a soft 404): `(app)/loading.tsx`
  streams the shell before `notFound()` runs. Content is never revealed; status code only.
- Fixed in Wave 5 (5.F2): a failed send keeps its specific reason + "Open Setup" link (`DraftView.failureCode`), and the client Canvas pre-check now returns `course_feed` / `private_address` like the server.
- `/email/[id]` (and `/setup` footer) leave an empty bordered block when `SENDBLUE_FROM_NUMBER` is unset (dev only): `TextAriaButton` renders nothing there.
- `next dev` only: server-action responses that overlap in time never finish streaming; the suite runs with `--workers=1` (see the 5.4 report).
- VoiceOver rotor / 200% zoom / real-device safe areas: still on the web plan §12 device list.
