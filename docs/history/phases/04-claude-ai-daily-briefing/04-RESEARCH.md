## User Constraints (from CONTEXT.md)

### Locked Decisions

**Briefing format & tone**
- Conversational prose — warm, casual, like a text from a knowledgeable friend. Not bullets, not robotic. Uses contractions, abbreviates course names, brief context (e.g. "your bio lab, the big one").
- Personality: Smart friend. Never sounds like a calendar alert or marketing message.
- Max length: 5 SMS segments (~800 chars). Claude must be prompted to stay under this limit.

**Monday extended briefing**
- Every Monday, the briefing expands to cover the full 7-day horizon: all deadlines in the next 7 days, exam topics stub (full topics added in Phase 7), and daily load score.
- GCal conflicts and available study windows are added in Phase 6 when GCal is connected.
- Monday briefing is generated by the same 7am job; the briefing generator detects `datetime.weekday() == 0` and switches to the extended prompt.

**Daily load score**
- Computed at briefing generation time: green (0–1 deadlines in 48h), yellow (2–3), red (4+).
- Included as a one-line summary in every briefing: e.g. "Heavy day ahead — 3 deadlines, 1 exam in 7 days."
- Feeds into iOS app Zone 2 status bar (Phase 8).

**Briefing content**
- Include: upcoming deadlines in next 48h (max 3–5 items), anything due this week (broader horizon), overdue items (flag separately), exam-specific callout when T-7 / T-5 / T-3 / T-1 / T-0 days out.
- Exam callout always surfaced with extra emphasis regardless of distance — e.g. "EXAM IN 7 DAYS: Chem midterm (Mar 26)".
- Canvas calendar events already in the DB may be included if present.
- Nothing-due day: send a short light message. Do not skip sending.

**Exam countdown logic**
- Exam countdown check runs as a Celery Beat job at 7am daily (SYNC-06).
- Countdown fires at T-7, T-5, T-3, T-1, and day-of (T-0).
- Countdown is bundled into the daily briefing — not a separate SMS.
- Exam identification uses the `type` field already set by `canvas/parse.py` (e.g. `type='exam'`). No re-parsing or Haiku classification needed.

**Welcome briefing**
- Trigger: Canvas iCal URL saved by the user during onboarding. Fire immediately.
- Content: Intro line ("Hey, I'm Aria! Here's what I see for you:") followed by regular briefing content.
- Late signup handling: Welcome briefing IS the "today's briefing" — do not also send a regular briefing that day.
- Sent via `send_sms_safe(is_proactive=True)` and counts toward the daily cap.

**Conversational reply scope**
- Supported: deadline queries, task management (mark complete, snooze via `snoozed_until`, set priority).
- Claude's context per reply: Last 14 days of deadlines from DB + last 5 SMS exchanges (from `messages` table) + the user's current message.
- Ambiguous task match: silently resolve to the soonest-due match.
- Off-topic messages: Friendly redirect.
- Conversational replies use `send_sms_safe(is_proactive=False)` — uncapped.

**Task management schema additions**
- `status` — already exists; mark-complete sets `status='completed'`
- `snoozed_until TIMESTAMPTZ` — new column; briefing generator skips items where `snoozed_until > now()`
- `priority VARCHAR DEFAULT 'normal'` — new column; values: `normal`, `high`; briefing generator surfaces high-priority items first

## Summary

Phase 4 integrates Claude Sonnet into the existing Celery pipeline to deliver three user-facing SMS behaviors: a scheduled daily briefing (7am generate, 8am send), a welcome briefing on Canvas URL save, and conversational replies to inbound SMS. All infrastructure from Phases 1–3 is already in place — the work is almost entirely additive Python code with no new Next.js routes.

The critical architectural decision is the **fan-out pattern for per-user timezone scheduling**. Celery Beat does not support per-user timezone natively. The established pattern in this codebase (already used for `canvas_sync_all`) is a Beat job that runs at a global time, fetches all users, and dispatches per-user Celery tasks that each handle their own timezone logic. For the 8am briefing, the generate task fires at 7am UTC but each worker task checks whether it is currently between 7:00–8:00am in the user's local timezone — only users in that window get generated/sent at this tick. Beat runs every 15 minutes as an alternative, or a single 7am job with each worker deferring sending via `send_sms_safe()`'s built-in quiet hours guard.

The simpler approach (and the one consistent with the existing codebase) is: Beat fires `generate_daily_briefings_all` at 7am UTC, each per-user task converts to local time and only generates if the user's local time is between 7:00–7:59am — quiet hours in `send_sms_safe()` handles the rest. This requires Beat to run more frequently (every 15 minutes) OR restrict to a single UTC window and accept ±timezone skew, OR use a different scheduling strategy described in Architecture Patterns below.

**Primary recommendation:** Use a crontab that fires every 15 minutes from 6am–12pm UTC; each per-user task checks whether the user's local time is in the 7:00–8:00am window before generating. This covers all US timezones (UTC-10 to UTC-5) within the scan window.

### Pattern 2: Conversation History in Messages Array
**What:** Pass last 5 SMS exchanges as alternating role messages before the current user message
**When to use:** Conversational reply handler (SMS-03, CONV-01)

```python
# Source: messages API — alternating user/assistant roles
# Fetch from DB: SELECT body, direction FROM messages
# WHERE user_id = %s ORDER BY sent_at DESC LIMIT 10
# Reverse to chronological order, map direction -> role

def build_history_messages(history_rows: list[dict]) -> list[dict]:
    """Convert DB rows (desc order) to SDK message format (asc order)."""
    role_map = {"in": "user", "out": "assistant"}
    messages = []
    for row in reversed(history_rows):  # oldest first
        role = role_map.get(row["direction"])
        if role:
            messages.append({"role": role, "content": row["body"] or ""})
    return messages
```

### Pattern 3: Celery Beat Fan-Out for Per-User Timezone Scheduling (SYNC-05)
**What:** Beat fires a "fan-out" task at a regular cadence; the fan-out task dispatches per-user tasks; each per-user task checks if the user's local time is in the target window
**When to use:** `generate_daily_briefings_all` (AI-05, AI-06)

```python
# In celery_app.py — add to beat_schedule:
from celery.schedules import crontab

"generate-daily-briefings": {
    "task": "tasks.generate_daily_briefings_all",
    "schedule": crontab(minute="*/15", hour="6-12"),  # every 15 min, 6am–12pm UTC
},
"exam-countdown-check": {
    "task": "tasks.exam_countdown_all",
    "schedule": crontab(hour=7, minute=0),  # once daily at 7am UTC
},
```

```python
# In generate_daily_briefings_all task:
from zoneinfo import ZoneInfo
from datetime import datetime, timezone

def _is_in_briefing_window(user: dict) -> bool:
    """True if user's local time is currently between 7:00–7:59am."""
    tz_name = (user.get("preferences_json") or {}).get("timezone", "America/New_York")
    local_now = datetime.now(ZoneInfo(tz_name))
    return local_now.hour == 7  # generate window: 7am local
```

**Key insight:** Beat running every 15 minutes means each user gets checked 4 times per hour. The `hour == 7` guard ensures generation only fires once (the first 15-min tick that lands in the 7am hour). To prevent double-generation, track last `briefing_sent_date` in `preferences_json` or a dedicated column — skip if already generated today.

```python
def compute_load_score(deadlines_48h: list[dict]) -> str:
    """Return 'green', 'yellow', or 'red' based on deadline count in next 48h."""
```

### Pattern 6: Exam Countdown Detection (SYNC-06)
**What:** Pure Python date arithmetic comparing each deadline's `due_date` against today
**When to use:** Inside the briefing generator; no separate SMS

```python
from datetime import datetime, timezone, timedelta

EXAM_TOUCHPOINTS = {7, 5, 3, 1, 0}  # days before exam

def get_exam_touchpoints(deadlines: list[dict], now: datetime) -> list[dict]:
    """Return exam deadlines that fall on a countdown touchpoint."""
    results = []
    for d in deadlines:
        if d.get("type") != "exam":
            continue
        due = datetime.fromisoformat(str(d["due_date"])).replace(tzinfo=timezone.utc)
        days_until = (due.date() - now.date()).days
        if days_until in EXAM_TOUCHPOINTS:
            results.append({**d, "days_until": days_until})
    return results
```

### Pattern 7: Task Management via SMS (AI-07)
**What:** Claude extracts intent and task reference from the message; Python code mutates the DB; Claude confirms with specific acknowledgment
**When to use:** Reply handler in `ai/replies.py`

Two-step approach:
1. Claude classifies intent AND identifies task (returns JSON: `{"action": "mark_complete", "task_hint": "bio lab"}`)
2. Python finds best match in DB (soonest-due matching title contains hint), mutates, confirms

```python
# Claude prompt for reply handling — ask for structured output
system_prompt = """You are Aria. Extract the user's intent from their SMS.
Return JSON only: {"action": "query"|"mark_complete"|"snooze"|"set_priority"|"off_topic",
                   "task_hint": "<partial task name or null>",
                   "priority_value": "normal"|"high"|null}"""
```

After DB mutation, call Claude again (or construct response directly) with the action result to generate a friendly confirmation.

**Alternative (simpler):** Use Claude to generate the full reply text — pass deadlines as context and ask Claude to both identify the action AND write the confirmation message. Simpler but harder to extract structured DB mutations. Recommendation: two calls or use Claude to return structured output first, then generate human reply second.

### Pattern 8: DB Query for Briefing Context
**What:** Fetch deadlines for briefing, replicating `canvas/db.py` pattern
**When to use:** `ai/briefing.py` and `ai/replies.py`

```python
# Fetch deadlines for briefing (last 14 days lookback + upcoming)
def get_deadlines_for_briefing(user_id: str, days_ahead: int = 7) -> list[dict]:
    client = _get_supabase()
    now = datetime.now(timezone.utc)
    cutoff = (now + timedelta(days=days_ahead)).isoformat()
    result = (
        client.table("deadlines")
        .select("id, title, due_date, course, type, grade_weight, status, priority, snoozed_until")
        .eq("user_id", user_id)
        .is_("deleted_at", "null")
        .neq("status", "completed")
        .lte("due_date", cutoff)
        .order("due_date", ascending=True)
        .execute()
    )
    # Filter out snoozed items
    active = [d for d in result.data if not _is_snoozed(d)]
    return active

def _is_snoozed(deadline: dict) -> bool:
    if not deadline.get("snoozed_until"):
        return False
    snooze_dt = datetime.fromisoformat(str(deadline["snoozed_until"]))
    return datetime.now(timezone.utc) < snooze_dt
```

### Anti-Patterns to Avoid
- **Calling Claude inline in the Next.js webhook:** The webhook must return 200 in <1s. All Claude calls go in Celery tasks.
- **Passing raw phone numbers to Claude:** Never include PII in prompts. Pass only `user_id` and deadline data.
- **Storing full conversation history:** Only last 5 exchanges (CONV-01). Do not grow unbounded.
- **Calling Twilio directly in `ai/` modules:** All outbound SMS goes through `send_sms_safe()`.
- **Building a custom SMS length calculator:** Use Claude's `max_tokens=300` to enforce output length, and instruct Claude in the system prompt to stay under 800 chars.
- **Re-parsing `type='exam'` with Haiku:** `canvas/parse.py` already sets this. Use it directly.
- **Sending welcome briefing + regular briefing on signup day:** Check for `trigger_type='welcome_briefing'` today before sending regular briefing.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Claude API request/response | Custom HTTP requests to api.anthropic.com | `anthropic` SDK `client.messages.create()` | Auto-retry on 429/500, typed responses, timeout handling built in |
| SMS character counting | Custom segmentation logic | Instruct Claude via max_tokens + system prompt char limit | Claude output length is controlled at the model level |
| Intent parsing for "mark bio lab done" | Custom NLP/regex | Claude with structured JSON output | Free-text variations are infinite; Claude handles them |
| Timezone conversion | Custom offset tables | `zoneinfo.ZoneInfo` (already used in `sms/send.py`) | Already in stdlib, already pattern-established |
| Conversation history truncation | Complex token counting | Limit to last 5 exchanges (10 rows) — well within Claude's context window | 10 short SMS messages are trivially small vs context window |
| Exam countdown triggers | Separate Celery Beat entries per touchpoint | Bundle into daily briefing generator with date arithmetic | Fewer Beat entries, one SMS per day, matches the spec |

**Key insight:** Claude handles all the ambiguity (free-text task names, varied query phrasing). Python handles structured mutations (DB updates, schema constraints). Keep these separated cleanly.

## Common Pitfalls

### Pitfall 1: Double-Briefing on Signup Day
**What goes wrong:** User signs up at 9am, gets welcome briefing. The 7am Beat job already ran but the per-user check runs again the next cycle (7:15am) and sends a second briefing.
**Why it happens:** The welcome briefing and the regular briefing run independently.
**How to avoid:** Before generating a regular briefing, query `messages` where `user_id = X AND trigger_type IN ('briefing', 'welcome_briefing') AND sent_at::date = today`. Skip if found.
**Warning signs:** Users reporting two morning messages on signup day.

### Pitfall 2: Claude Exceeding 800-Char SMS Limit
**What goes wrong:** Claude generates a briefing that is 1,200 chars and gets split into 6 SMS segments, incurring extra Twilio cost.
**Why it happens:** `max_tokens=300` limits tokens, not characters. Token/char ratio varies.
**How to avoid:** In the system prompt: "Your response MUST be under 800 characters total. Count carefully." Also validate `len(text) <= 800` before sending; truncate with "..." if over.
**Warning signs:** Twilio bills showing unexpectedly high segment counts.

### Pitfall 3: Celery Beat Double-Firing in 7am Window
**What goes wrong:** Beat runs every 15 minutes; the per-user task fires at both 7:00am and 7:15am for a user whose local time is 7:00am (both land in `hour == 7`).
**Why it happens:** Both ticks have `local_now.hour == 7`.
**How to avoid:** Use a `briefing_sent_date` column on `users` (or check `messages` table for today's entry). Write this at generation time, not send time.
**Warning signs:** Users receiving two identical briefings in the morning.

### Pitfall 4: All-Day Canvas Events Showing Wrong Countdown
**What goes wrong:** Canvas exam stored as 23:59:59Z (Phase 2 normalization); `days_until` calculation shows T-0 a day early when computed in EST (UTC-5).
**Why it happens:** 23:59:59 UTC is 6:59pm EST the same day, but `due.date()` in UTC is correct — the issue is comparing `now.date()` (user's local date) against `due.date()` (UTC date).
**How to avoid:** Convert both `now` and `due` to the user's local timezone before computing `days_until`. Use `due.astimezone(user_tz).date()`.
**Warning signs:** T-1 exam reminders firing the evening of the exam day instead of the night before.

### Pitfall 5: `anthropic.RateLimitError` Blocking Celery Tasks
**What goes wrong:** When briefings are generated for many users simultaneously, Anthropic rate limits fire and tasks fail.
**Why it happens:** Anthropic's default tier has rate limits; fan-out to 50 simultaneous users could exceed them.
**How to avoid:** The SDK auto-retries 429s twice by default. Also add `autoretry_for=(anthropic.RateLimitError,)` to the Celery task with `retry_backoff=True`. For 50 users (MVP scale), this is unlikely to be an issue.
**Warning signs:** Tasks failing with `RateLimitError` in Celery logs.

### Pitfall 6: `snoozed_until` Not Filtering Correctly
**What goes wrong:** Briefing shows an item the user snoozed yesterday.
**Why it happens:** DB query doesn't filter on `snoozed_until`, or the Python filter compares naive vs aware datetimes.
**How to avoid:** Always use timezone-aware `datetime.now(timezone.utc)` in the snooze comparison. Ensure `snoozed_until` is stored as TIMESTAMPTZ.
**Warning signs:** Snoozed items reappearing in briefings.

### Pitfall 7: Conversation History Role Ordering
**What goes wrong:** SDK raises `Invalid role order` error or Claude gets confused context.
**Why it happens:** The messages array must alternate user/assistant roles starting with user. DB rows ordered DESC need reversing; messages table may have consecutive `direction='out'` entries.
**How to avoid:** Reverse the DESC rows to get chronological order, then deduplicate consecutive same-role messages by keeping the most recent.
**Warning signs:** `anthropic.BadRequestError` on the messages call.

## Code Examples

### Anthropic SDK — Full Briefing Call Pattern
```python
# Source: https://platform.claude.com/docs/en/api/sdks/python (verified 2026-03-18)
import os
import json
import logging
import hashlib
from anthropic import Anthropic, RateLimitError

logger = logging.getLogger(__name__)

def call_claude_for_briefing(
    user_id: str,
    system_prompt: str,
    context_text: str,
    max_tokens: int = 300,
) -> str:
    """Call Claude Sonnet and return the generated text.

    Args:
        user_id: UUID — used for hashed logging only, never sent to Claude.
        system_prompt: The Aria persona + output constraints.
        context_text: Deadline data formatted as text.
        max_tokens: Token budget (300 ≈ 900 chars max output).

    Returns:
        Generated briefing text string.
    """
    client = Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
    hashed_id = hashlib.sha256(user_id.encode()).hexdigest()[:12]

    import time
    start = time.monotonic()
    response = client.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=max_tokens,
        system=system_prompt,
        messages=[{"role": "user", "content": context_text}],
    )
    latency_ms = int((time.monotonic() - start) * 1000)

    logger.info(json.dumps({
        "event": "claude_call",
        "uid": hashed_id,
        "input_tokens": response.usage.input_tokens,
        "output_tokens": response.usage.output_tokens,
        "latency_ms": latency_ms,
    }))

    return response.content[0].text
```

```python
- "mark_complete" for done/finished/completed ("mark bio lab done", "finished econ pset")
- "snooze" for snooze/remind me later ("snooze chem hw", "not now for bio")
- "set_priority" for priority changes ("high priority econ pset", "urgent: calc midterm")
- "off_topic" for anything not deadline-related
- task_hint: extract the course/assignment name fragment, lowercase"""
```

- `anthropic.Completion`: The old completions API is gone. Use `client.messages.create()`.

## Open Questions

1. **Welcome briefing trigger location**
   - What we know: The trigger should fire "immediately when Canvas iCal URL is saved." Phase 3's Next.js webhook returns 202 immediately; direct Celery enqueue from Next.js is deferred to Phase 7.
   - What's unclear: Where exactly to trigger `welcome_briefing.delay(user_id)` — from `canvas_sync_user` task after first successful sync (detecting first sync via `integrations.synced_at IS NULL` before the call), or from a separate API route.
   - Recommendation: Detect first sync inside `canvas_sync_user` by checking if `synced_at` was NULL before `mark_synced()` runs. If first sync, enqueue `welcome_briefing.delay(user_id)`. This is fully within the Celery worker, no Next.js changes needed.

2. **Double-generation prevention mechanism**
   - What we know: Beat fires every 15 minutes; per-user `hour == 7` check fires up to 4 times.
   - What's unclear: Best place to track "already generated today" — new column on `users` vs query `messages` table.
   - Recommendation: Query `messages` table for `trigger_type='briefing' AND sent_at::date = today` — avoids a new column. Slightly slower but simpler schema.

3. **`exam_countdown_all` vs bundling into `generate_daily_briefings_all`**
   - What we know: CONTEXT.md says exam countdown is bundled into the daily briefing, not a separate SMS. SYNC-06 lists it as a separate Beat entry.
   - What's unclear: Whether `exam_countdown_all` is a separate Beat task or just a function called inside `generate_daily_briefings_all`.
   - Recommendation: Implement as a function `get_exam_touchpoints()` called inside the briefing generator. The Beat entry `exam-countdown-check` can be the same as `generate-daily-briefings` — they share the same 7am fan-out. Add a single Beat entry for briefings that handles both.
